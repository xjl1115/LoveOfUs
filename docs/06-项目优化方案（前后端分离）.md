# LoveOfUs 项目优化方案

## 文档说明

本文档基于 LoveOfUs 项目现有代码库进行系统性分析，分别从 **前端** 和 **后端** 两个维度梳理当前存在的可优化点，并给出对应的优化建议与实施方向。文档侧重于工程实践层面的改进，不涉及新功能设计。

---

## 一、前端优化

### 1.1 安全优化

#### 1.1.1 Token 存储方式

**当前实现：**
- 当前代码注释中提到使用 `sessionStorage` 替代 `localStorage`，但实际 `secureStorage` 仍调用 `localStorage`。
- 见 [src/stores/user.ts](file:///e:/java/program/LoveOfUs/loveofus-frontend/src/stores/user.ts) 中的 `secureStorage` 实现。

**优化建议：**
- 真正改用 `sessionStorage` 或实现 httpOnly Cookie 方案。
- 若使用 Cookie，需配置 `SameSite=Strict` 和 `Secure` 属性。
- 避免将 Token 持久化在 localStorage 中，降低 XSS 攻击后的横向移动风险。

#### 1.1.2 Token 过期判断时机

**当前实现：**
- 请求拦截器中判断 Token 是否过期，若过期直接登出并重定向到登录页。

**优化建议：**
- 对于即将过期但仍在有效期内的 Token，优先触发刷新，而非直接拦截请求。
- 当前逻辑中，过期 Token 会先被拦截器拒绝，无法进入 401 重试流程。
- 可在拦截器中区分“已过期”和“即将过期”两种情况，后者尝试静默刷新。

#### 1.1.3 生产环境日志输出

**当前实现：**
- 路由守卫中仍存在 `logger.debug` 等日志输出，虽然通过 `import.meta.env.DEV` 做了限制，但 `logger.error` 仍会打印到控制台。

**优化建议：**
- 生产环境完全禁用 console 输出，或接入 Sentry 等错误上报平台。
- 使用环境变量统一控制日志级别。

### 1.2 代码结构优化

#### 1.2.1 单文件组件过大

**当前实现：**
- [src/views/Profile.vue](file:///e:/java/program/LoveOfUs/loveofus-frontend/src/views/Profile.vue) 超过 700 行，同时包含用户资料、伴侣绑定、纪念日管理、通知设置、照片展示等多个功能模块。

**优化建议：**
- 将纪念日管理、通知设置、绑定码管理等拆分为独立子组件。
- 提升代码可读性和复用性，降低单文件维护成本。

#### 1.2.2 API 层类型定义

**当前实现：**
- 部分 API 文件直接内联定义请求参数类型，未统一抽离。

**优化建议：**
- 将所有 DTO/VO 类型统一放置在 `src/types` 目录下。
- 避免在 API 层与组件层重复定义类型。

#### 1.2.3 状态管理拆分

**当前实现：**
- 所有用户相关状态集中在 `userStore` 中，包括 Token、用户信息、活跃时间等。

**优化建议：**
- 将认证状态（Token、refreshToken）与业务状态（userInfo、daysTogether）拆分到不同 Store。
- 便于模块化和测试。

### 1.3 性能优化

#### 1.3.1 图片懒加载

**当前实现：**
- 已存在 `v-lazy` 自定义指令，但未确认是否全局应用到所有照片列表。

**优化建议：**
- 在时间线、相册详情、足迹地图等照片密集场景统一启用懒加载。
- 对首屏可见图片做 `preload` 或 `prefetch`。

#### 1.3.2 组件按需加载

**当前实现：**
- 路由已使用动态导入，但部分大体积依赖（如 echarts）可能未按需加载。

**优化建议：**
- 对 echarts、qrcode 等重型依赖使用动态导入。
- 避免在应用启动时一次性加载所有依赖。

#### 1.3.3 keep-alive 缓存

**当前实现：**
- 未在路由中配置 `keep-alive`。

**优化建议：**
- 对首页、相册列表等用户频繁往返的页面启用 `keep-alive`。
- 减少重复请求和数据重渲染。

#### 1.3.4 虚拟滚动

**当前实现：**
- 已存在 `VirtualPhotoList.vue` 组件，但未确认是否被全面使用。

**优化建议：**
- 对时间线、搜索结果等长列表统一使用虚拟滚动。
- 避免大量 DOM 节点导致的渲染性能问题。

### 1.4 交互体验优化

#### 1.4.1 请求错误提示

**当前实现：**
- 响应拦截器中所有非 200 响应统一调用 `showToast`。

**优化建议：**
- 对 401、403、500 等错误做差异化提示。
- 对并发请求导致的重复 Toast 进行去重或队列控制。

#### 1.4.2 加载状态管理

**当前实现：**
- 部分页面使用独立的 `loading` 变量管理加载状态。

**优化建议：**
- 引入全局 Loading 状态管理，避免重复实现。
- 对长时间操作（导出、批量上传）提供进度提示。

#### 1.4.3 表单校验

**当前实现：**
- 纪念日、绑定码等表单校验逻辑分散在组件中。

**优化建议：**
- 使用 VeeValidate 或自定义 composable 统一表单校验规则。
- 抽离通用校验函数（手机号、日期、必填等）。

### 1.5 构建与部署优化

#### 1.5.1 构建产物体积

**当前实现：**
- 构建日志显示 `echarts` 打包后超过 1MB，部分 chunk 超过 500KB。

**优化建议：**
- 使用 CDN 加载 echarts、vue、vant 等库。
- 开启 `rollup-plugin-visualizer` 分析产物体积。
- 对非首屏依赖做动态分割。

#### 1.5.2 环境变量管理

**当前实现：**
- 环境变量通过 `.env` 文件管理，但未确认是否有生产环境专用配置。

**优化建议：**
- 明确区分 `.env.development`、`.env.production`、`.env.test`。
- API 基础地址、上传大小限制等通过环境变量注入。

## 二、后端优化

### 2.1 安全优化

#### 2.1.1 JWT Token 刷新机制

**当前实现：**
- 后端提供 `/api/auth/token/refresh` 接口，但前端实现了一个 `doRefreshToken` 方法，使用 `fetch` 直接调用，绕过了 axios 拦截器的统一处理。

**优化建议：**
- 后端应明确返回 Token 过期前的刷新窗口，避免前端频繁刷新。
- 后端可考虑双 Token 策略：Access Token 短期有效，Refresh Token 长期有效。
- 对 Refresh Token 也设置过期时间，并支持黑名单机制。

#### 2.1.2 Token 黑名单清理

**当前实现：**
- Token 黑名单存储在 Redis 中，未设置过期时间。

**优化建议：**
- 黑名单中的 Token 只需保留到原 Token 过期时间即可。
- 为黑名单 Key 设置与原 Token 剩余有效期一致的 TTL。
- 减少 Redis 内存占用。

#### 2.1.3 登录失败次数限制

**当前实现：**
- 登录接口未做失败次数限制。

**优化建议：**
- 使用 Redis 记录连续登录失败次数，超过阈值后临时锁定账号。
- 对验证码发送接口做 IP 级别限流。

#### 2.1.4 敏感接口权限校验

**当前实现：**
- 多数接口通过 JWT 获取 userId，但未显式校验用户是否为资源所有者。

**优化建议：**
- 在 Service 层增加数据归属校验，防止越权访问。
- 例如：查询纪念日详情时，需校验该纪念日是否属于当前用户或伴侣。

### 2.2 性能优化

#### 2.2.1 SSE 连接超时与 Nginx 配置

**当前实现：**
- [SseService.java](file:///e:/java/program/LoveOfUs/LoveMap/src/main/java/com/example/lovemap/service/SseService.java) 中 SSE 超时时间为 30 分钟。
- Nginx 配置中 SSE 路径的 `proxy_read_timeout` 已设置为 1800 秒，与后端保持一致。

**优化建议：**
- 30 分钟是合理设置，无需修改。
- 但应确保 Nginx 的 `proxy_buffering off` 和 `proxy_cache off` 配置生效。
- 增加心跳机制，建议每 30 秒发送一次心跳包，防止中间件提前断开连接。

#### 2.2.2 照片上传与处理

**当前实现：**
- 照片上传到阿里云 OSS，存在异步上传逻辑。

**优化建议：**
- 上传前在客户端进行图片压缩，减少带宽和服务器压力。
- 服务端生成多尺寸缩略图（thumbnail/small/medium），避免前端直接加载原图。
- 对重复照片基于文件 MD5 做去重处理。

#### 2.2.3 数据库查询优化

**当前实现：**
- 部分时间线查询未使用覆盖索引。

**优化建议：**
- 对 `photo` 表的 `(user_id, taken_date, is_deleted)` 建立联合索引。
- 对 `notification` 表的 `(user_id, is_read, created_at)` 建立联合索引。
- 避免 `SELECT *`，只查询必要字段。

#### 2.2.4 缓存策略

**当前实现：**
- 已使用 Redis 缓存用户信息、相册详情等。

**优化建议：**
- 对热点数据设置合理的过期时间，避免缓存雪崩。
- 增加缓存预热和缓存穿透防护（空值缓存或布隆过滤器）。
- 对相册列表、用户统计等数据使用缓存，但需注意缓存一致性。

### 2.3 代码质量优化

#### 2.3.1 异常处理统一性

**当前实现：**
- `SecurityConfig` 中 `authenticationEntryPoint` 方法存在一行无效代码：
  ```java
  new ObjectMapper().writeValueAsString(result);
  ```
  该调用结果未被使用。

**优化建议：**
- 删除无效代码行。
- 统一异常响应格式，避免重复创建 `ObjectMapper` 实例。

#### 2.3.2 常量管理

**当前实现：**
- 存在多个 `Constant` 类，但部分硬编码值仍分散在业务代码中。

**优化建议：**
- 将 Redis Key 前缀、Token 过期时间、分页默认值等统一抽离到常量类。
- 避免魔法值和重复字符串。

#### 2.3.3 日志规范

**当前实现：**
- 部分代码中 `log.debug` 输出中文日志，部分使用英文。

**优化建议：**
- 统一日志语言（建议英文）。
- 关键操作（登录、绑定、注销、删除）记录审计日志。
- 避免在日志中打印敏感信息（Token、密码、验证码）。

#### 2.3.4 方法复杂度控制

**当前实现：**
- 部分 Service 方法行数超过 80 行，例如导出功能、批量上传功能等。

**优化建议：**
- 将复杂方法拆分为多个职责单一的小方法。
- 使用策略模式处理不同导出格式（ZIP/PDF/Video）。

### 2.4 数据库与存储优化

#### 2.4.1 软删除与数据归档

**当前实现：**
- `photo` 表已支持 `is_deleted` 软删除。

**优化建议：**
- 对软删除数据定期归档或清理，避免表数据无限增长。
- 为软删除字段增加索引，优化查询性能。

#### 2.4.2 导出记录表

**当前实现：**
- 后端存在 `ExportRecord` 实体，但导出功能可能未完全实现。

**优化建议：**
- 完善导出任务状态流转（pending / processing / completed / failed）。
- 对失败任务支持重试和手动触发。
- 定期清理过期导出文件。

#### 2.4.3 通知表设计

**当前实现：**
- `notification` 表包含 `group_id`、`business_id` 等字段。

**优化建议：**
- 明确 `group_id` 的业务含义，若当前未使用建议移除或加注释说明。
- 对大量通知数据按时间分表或归档。

### 2.5 运维与监控优化

#### 2.5.1 健康检查

**当前实现：**
- 文档中提到 Spring Boot Actuator，但未确认是否已引入依赖。

**优化建议：**
- 引入 `spring-boot-starter-actuator` 并暴露健康端点。
- 配置 MySQL、Redis、MinIO 等依赖组件的健康检查。

#### 2.5.2 异步任务监控

**当前实现：**
- 已配置多个线程池（验证码、照片上传、导出、通知）。

**优化建议：**
- 暴露线程池活跃度、队列大小等指标。
- 对任务执行时间做监控和告警。

#### 2.5.3 Nginx 日志与缓存

**当前实现：**
- Nginx 已配置 access_log 和错误页面。

**优化建议：**
- 对静态资源增加更细粒度的缓存策略。
- 启用 Nginx 访问日志的按天切割，避免单文件过大。
- 监控 Nginx 后端节点的健康状态。

## 三、前后端协作优化

### 3.1 接口规范统一

**当前问题：**
- 部分接口返回字段命名未统一（如前端 `daysLeft` 与后端 `daysUntil`）。
- 部分功能前端已实现但后端接口缺失（如早期的导出功能、AI 功能）。

**优化建议：**
- 制定统一的接口字段命名规范（camelCase / snake_case）。
- 使用 Swagger/OpenAPI 文档作为前后端契约。
- 接口变更前同步更新文档。

### 3.2 错误码统一

**当前实现：**
- 后端已定义 `ResultCode` 枚举。

**优化建议：**
- 前端根据后端错误码做精准提示，而不是仅显示 message。
- 对常见错误码（401、403、404、422、429）制定统一处理策略。

### 3.3 版本管理

**优化建议：**
- 对接口进行版本控制（如 `/api/v1/...`）。
- 避免接口变更导致旧版本前端不可用。

## 四、优化优先级建议

| 2 | 删除 SecurityConfig 无效代码 | 后端 | 清理重复 ObjectMapper 调用 |
| 3 | 增加登录失败次数限制 | 后端 | 防止暴力破解 |
| 4 | 拆分 Profile.vue 大组件 | 前端 | 提升可维护性 |
| 5 | 增加数据归属校验 | 后端 | 防止越权访问 |

| 序号 | 优化项 | 所属端 | 说明 |

| 3 | 统一类型定义 | 前端 | 抽离 DTO/VO 类型 |
| 4 | 接入健康检查 | 后端 | 完善运维监控 |

| 序号 | 优化项 | 所属端 | 说明 |
|------|--------|--------|------|
| 1 | 构建产物优化 | 前端 | CDN、按需加载 |

| 3 | 接口版本控制 | 后端 | 支持多版本共存 |

## 五、总结

LoveOfUs 项目整体架构清晰，功能实现较为完整，但仍存在一些工程实践层面的优化空间。前端的重点在于 **安全性（Token 存储）、组件拆分、性能优化**；后端的重点在于 **安全校验、代码质量、数据库性能、监控运维**。建议按照优先级逐步推进，优先解决安全风险和维护成本高的问题，再逐步完善性能和扩展性。
